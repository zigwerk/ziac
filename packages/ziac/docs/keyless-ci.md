# Keyless GitHub Preview Deployments

Ziac ships a copyable GitHub Actions workflow at
`examples/github-actions/ziac-preview.yml`. It plans, deploys, and cleans up
repository-bound pull-request previews with Google Workload Identity
Federation, GCS state, and immutable Ziac plans.

The template is intentionally not active under `.github/workflows`. Copy it
only after configuring the Google trust policy, bucket, DNS, repository
variables, and GitHub Environments described below.

## Trust Model

The workflow requests only:

```yaml
permissions:
  contents: read
  id-token: write
```

`google-github-actions/auth@v3` exchanges the GitHub OIDC assertion for a
short-lived Google token and writes an external-account ADC file. Ziac reads
that file natively through `GOOGLE_APPLICATION_CREDENTIALS`; it does not invoke
`gcloud` and does not need a downloaded service-account key.

Google recommends Workload Identity Federation over service-account key JSON.
The action also requires checkout before authentication when it creates the ADC
file. See the current [Google auth action](https://github.com/google-github-actions/auth)
and [Google deployment-pipeline WIF guide](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines).

The template refuses fork-originated PR code before the job receives an ID
token:

```text
github.event.pull_request.head.repo.full_name == github.repository
```

Plan, deploy, and cleanup use separate GitHub Environments. Configure required
reviewers, branch policy, and environment-specific variables there. The WIF
provider must independently restrict admission; workflow conditions are not an
IAM boundary.

## Google Setup

Create a workload identity pool and GitHub OIDC provider. Map at least:

```text
google.subject=assertion.sub
attribute.repository=assertion.repository
attribute.repository_owner=assertion.repository_owner
attribute.workflow_ref=assertion.job_workflow_ref
```

Use an attribute condition that pins the repository and copied workflow, for
example:

```text
assertion.repository == 'owner/repository' &&
assertion.job_workflow_ref.startsWith(
  'owner/repository/.github/workflows/ziac-preview.yml@'
)
```

If using service-account impersonation, grant `roles/iam.workloadIdentityUser`
on the deployment service account only to the repository principal set. Grant
that service account the smallest resource-scoped permissions needed by the
selected Ziac stack and state bucket. Avoid project-wide owner/editor roles.

The GCS state identity needs `storage.objects.get`,
`storage.objects.create`, and `storage.objects.delete` on the state bucket. See
`remote-state.md` for bucket hardening and recovery.

## Repository Variables

Configure these GitHub repository or environment variables:

| Variable | Purpose |
| --- | --- |
| `GCP_PROJECT_ID` | Target Google project ID |
| `GCP_WIF_PROVIDER` | Full `projects/<number>/locations/global/workloadIdentityPools/.../providers/...` name |
| `GCP_ZIAC_SERVICE_ACCOUNT` | Short-lived impersonation target email |
| `GCP_PRIMARY_REGION` | Primary Cloud Run region |
| `GCP_SERVICE_REGIONS` | Comma-separated global service regions |
| `ZIAC_PREVIEW_IMAGE` | Immutable Artifact Registry image digest |
| `ZIAC_BASE_DOMAIN` | Base application domain; Ziac adds the preview label |
| `ZIAC_DNS_ZONE` | Existing Cloud DNS managed-zone name |
| `ZIAC_STATE_BUCKET` | Hardened GCS state bucket |
| `ZIAC_STATE_PREFIX` | Non-empty state prefix, normally `ziac/state` |

The WIF provider resource name and service-account email are identifiers, not
private credentials. Do not add `credentials_json`, a private key, or a Google
service-account key secret. The repository `.gitignore` and Zig source archiver
both exclude `gha-creds-*.json`, the temporary file pattern generated by the
auth action.

## Preview Identity

Derive the stage through Ziac rather than duplicating naming logic in shell:

```sh
stage="$(zig-out/bin/ziac preview-stage \
  --repository "$GITHUB_REPOSITORY" \
  --change "$PR_NUMBER")"
```

For `Acme/Platform` PR 42, the result is:

```text
pr-42-9333e523
```

The repository hash prevents collisions when several repositories share a
project or bucket. GCS state uses that exact stage. The built-in
`hello-global` and `global-container` stacks also scope preview-owned resource
names and publish `<stage>.<base-domain>`.

Custom stack code should use:

```zig
const service_name = try ziac.ci.scopedResourceNameAlloc(
    allocator,
    "api",
    stage,
    49,
);
const domain = try ziac.ci.previewDomainAlloc(
    allocator,
    "api.example.com",
    stage,
);
```

Persistent stages return the original base names for compatibility. Strings
that begin with `pr-` but do not match the canonical grammar fail rather than
silently behaving as persistent stages.

## Plan And Deploy

The plan job performs live provider reads and writes a create-exclusive plan:

```sh
ziac plan \
  --stack global-container \
  --stage "$stage" \
  --provider gcp \
  --allow-live \
  --out "$RUNNER_TEMP/ziac-plan/preview.plan.json" \
  --json
```

The plan and receipt are uploaded by `actions/upload-artifact@v7` with
`overwrite: false`. Current GitHub artifact implementations are immutable; see
the [official upload-artifact project](https://github.com/actions/upload-artifact).

The protected deploy job checks out the exact same commit, downloads that
artifact, verifies the receipt digest, and runs `deploy --plan`. If the plan is
destructive, it passes the exact reviewed digest through `--approve`. State
serial, graph digest, operation integrity, writer lease, and GCS generation CAS
remain active.

## Cleanup

On PR close, the cleanup job recomputes the same stage and runs:

```sh
ziac destroy \
  --stack global-container \
  --stage "$stage" \
  --provider gcp \
  --allow-live \
  --preview-cleanup \
  --confirm
```

`--preview-cleanup` accepts only the exact canonical preview grammar. It rejects
`prod`, `production`, ordinary persistent stages, and malformed `pr-` strings
before provider selection or lock acquisition. It does not bypass lifecycle
protection. Preview stacks should adopt shared protected CockroachDB data or use
explicitly disposable unprotected data resources.

Failed cleanup leaves remote state and lock/recovery behavior intact. Inspect
state, resolve the provider error, and rerun the same deterministic stage.
